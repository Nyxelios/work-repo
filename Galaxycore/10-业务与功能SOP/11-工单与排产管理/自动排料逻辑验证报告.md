# MES自动排料逻辑验证报告

## 1. 概述

本报告对 Galaxycore MES 系统中的自动排料定时任务进行了全面正确性验证，包括 `CpAutoPlanJob` (CP自动排料) 和 `WltAutoPlanJob` (WLT自动排料) 两个核心组件。

### 1.1 验证范围

| 组件 | 文件路径 | 说明 |
|------|----------|------|
| CpAutoPlanJob | `d:\data\gc\core\src\gc\src\main\java\com\mycim\gc\service\quartz\jobs\CpAutoPlanJob.java` | CP产线自动排料定时任务 |
| WltAutoPlanJob | `d:\data\gc\core\src\gc\src\main\java\com\mycim\gc\service\quartz\jobs\WltAutoPlanJob.java` | WLT产线自动排料定时任务 |
| WorkOrderPlanServiceImpl | `d:\data\gc\core\src\gc\src\main\java\com\mycim\gc\service\impl\WorkOrderPlanServiceImpl.java` | 排料业务逻辑实现 |

### 1.2 业务背景

自动排料是MES系统的核心功能，用于根据配置自动将晶圆批次(Wafer Lot)分配到相应的工单(Work Order)中，涉及：
- CP (Chip Probing): 晶圆测试产线
- WLT (Wafer Level Test): 晶圆级测试产线
- RW (Rework): 返工产线

## 3. 核心问题发现

### 严重问题

#### 3.1 并发控制机制存在严重缺陷

**问题描述:**
两个Job类都使用 `static int lockKey` 作为锁标志，存在以下问题：

```java
// 问题代码
static int lockKey=0;

public synchronized void execute(JobExecutionContext context) {
    if(lockKey>0){
        return;
    }
    lockKey=1;
    // ... 业务逻辑
    finally {
        lockKey=0;
    }
}
```

**问题分析:**

| 问题             | 风险等级 | 说明                                                          |
| -------------- | ---- | ----------------------------------------------------------- |
| 非原子性操作         | 高    | `if(lockKey>0)` 和 `lockKey=1` 之间可能被其他线程插入                   |
| 静态变量共享         | 高    | CpAutoPlanJob 和 WltAutoPlanJob 各自有独立的lockKey，但同一Job类的多个实例共享 |
| 异常时锁不释放        | 高    | 如果在 `lockKey=1` 之后、`finally` 之前发生系统崩溃，锁将永久丢失                |
| synchronized冗余 | 中    | 方法已加synchronized，lockKey检查是多余的                              |

**改进建议:**
```java
// 推荐方案1: 使用ReentrantLock
private static final ReentrantLock lock = new ReentrantLock();

public void execute(JobExecutionContext context) {
    if (!lock.tryLock()) {
        log.warn("排料任务正在执行，跳过本次调度");
        return;
    }
    try {
        // 业务逻辑
    } finally {
        lock.unlock();
    }
}

// 推荐方案2: 使用分布式锁（集群环境）
// 使用Redis或数据库实现分布式锁
```

#### 3.2 CpAutoPlanJob 中 errFlag 逻辑错误

**问题代码:**
```java
boolean errFlag=false;  // 初始化为false
try {
    // ... 排料逻辑，没有地方设置 errFlag = true
} catch (Exception e) {
    // ... 异常处理
} finally {
    if(errFlag){  // 永远为false
        msgList.add(errMsg);
    }
}
```

**问题:** `errFlag` 初始化为 `false`，且在try块中从未被设置为 `true`，导致 `finally` 块中的错误消息收集逻辑永远不会执行。

**改进建议:**
```java
try {
    // ...
} catch (Exception e) {
    errFlag = true;  // 添加这行
    log.error(e.getMessage(), e);
    errMsg=errMsg+e.getMessage();
    throw ExceptionHandler.handlerException(e);
}
```

#### 3.3 WltAutoPlanJob 缺少排料结束日志记录

**问题:** WltAutoPlanJob 在 finally 块中只释放了锁，没有记录排料结束日志，而 CpAutoPlanJob 有完整的日志记录。

**改进建议:**
```java
finally {
    // 添加结束日志记录
    GcAutoPlanLog endLog = new GcAutoPlanLog();
    endLog.setTransTime(new Date());
    endLog.setLogInfo("WLT排料结束" + System.currentTimeMillis());
    gcServiceImpl.saveAutoLog(endLog);
    
    if(CollectionUtils.isNotEmpty(prodList)){
        gcServiceImpl.sendWltAutoMsgInfo(prodList);
    }
    lockKey=0;
}
```

### 中等问题

#### 3.4 服务器白名单硬编码

**问题代码:**
```java
if(!StringUtils.equals(serverId,"MESAP01")
        &&!StringUtils.equals(serverId,"MESAP02")
        &&!StringUtils.equals(serverId,"RWAP01")
        &&!StringUtils.equals(serverId,"RWAP02")){
    //非生产环境不能跑定时任务
    return;
}
```

**问题:**
- 服务器名称硬编码，维护困难
- 环境判断逻辑与业务代码耦合
- 无法动态配置

**改进建议:**
```java
// 使用配置中心或环境变量
@Value("${autoplan.allowedServers:MESAP01,MESAP02,RWAP01,RWAP02}")
private String allowedServers;

private boolean isAllowedServer(String serverId) {
    Set<String> allowed = new HashSet<>(Arrays.asList(allowedServers.split(",")));
    return allowed.contains(serverId);
}
```

#### 3.5 日期格式化线程安全问题

**问题代码 (CpAutoPlanJob):**
```java
SimpleDateFormat formatter = new SimpleDateFormat("yyyy-MM-dd");
String formattedDate = formatter.format(new Date());
```

**问题:** `SimpleDateFormat` 不是线程安全的，虽然这里每次调用都创建新实例，但更好的做法是使用 `DateTimeFormatter`。

**改进建议:**
```java
// Java 8+ 推荐方式
private static final DateTimeFormatter DATE_FORMATTER = DateTimeFormatter.ofPattern("yyyy-MM-dd");

String formattedDate = LocalDate.now().format(DATE_FORMATTER);
```

#### 3.6 事务边界不清晰

**问题:** Job类中没有显示的事务控制，所有数据库操作依赖底层Service的事务管理。如果某个配置排料失败，可能导致部分数据不一致。

**改进建议:**
- 每个配置的排料应该在独立的事务中执行
- 使用 `@Transactional(propagation = Propagation.REQUIRES_NEW)` 确保单个配置失败不影响其他配置

### 轻微问题

#### 3.7 日志信息格式不一致

**问题:** 两个Job类的日志格式不一致，有的包含时间戳，有的不包含。

#### 3.8 缺少执行结果统计

**问题:** 没有统计成功/失败的配置数量，不利于监控和告警。

## 4. 业务逻辑验证

### 4.1 CP排料逻辑 (cpAutoPlan)

#### 4.1.1 流程验证

```
1. 验证配置有效性 (GcModelManagement)
   └── 配置无效 → 关闭配置 + 记录日志 + 返回错误消息

2. 拼接查询代码 (splicingCpCode)
   └── 处理通配符 (*) 转换为下划线 (_)

3. 查询待排料批次 (getCpAutoPlanLot)
   └── 无批次 → 记录日志 + 返回错误消息

4. 批次分组和过滤
   ├── 按物料属性分组 (key = materialName + reserved6 + reserved50 + reserved1 + factoryId)
   ├── 检查保税属性 (bonded)
   └── 检查是否已绑定工单 (WorkOrderRelation)

5. 数量控制
   └── 累计数量不能超过 planQty

6. 执行排料 (cpAutoPlanInfo)
   └── 创建工单 + 创建LotPlan + 更新物料批次

7. 更新配置状态
   ├── 设置 inputQty
   ├── 关闭配置 (isOpen=0)
   └── 保存历史记录
```

#### 4.1.2 发现的问题

| 问题 | 说明 | 建议 |
|------|------|------|
| 数量计算精度 | 使用 BigDecimal 进行数量计算，但最终转换为int | 确认是否会有精度损失 |
| 部分排料处理 | 如果累计数量超过planQty，超出部分被忽略 | 需要确认业务是否接受 |
| 配置关闭逻辑 | CP排料完成后自动关闭配置 | 确认是否所有场景都需要关闭 |

### 4.2 WLT排料逻辑 (wltAutoPlan)

#### 4.2.1 流程验证

```
1. 验证配置有效性 (GcModelManagement)
   └── 配置无效 → 关闭配置 + 记录日志 + 返回产品ID

2. 验证配置一致性
   └── 测试型号或流程ID不匹配 → 关闭配置 + 记录日志

3. 拼接查询代码 (splicingWltCode)

4. 查询待排料批次 (getWltAutoPlanLot)

5. 批次过滤
   ├── 检查 WorkOrderRelation 绑定
   ├── 检查 LotPlan 已排料状态
   └── 累计 inputQty

6. 执行排料 (wltAutoPlanInfo)
   └── 创建工单 + 创建Lot + 创建LotPlan

7. 更新配置状态
   └── 设置 inputQty + 保存历史记录
```

#### 4.2.2 发现的问题

| 问题 | 说明 | 建议 |
|------|------|------|
| 无批次处理 | 没有查询到批次时只记录日志，没有返回标识 | 建议返回特定消息 |
| 工单数量更新 | 在else分支中更新工单数量，但代码复杂 | 需要验证逻辑正确性 |

### 4.3 RW排料逻辑 (rwAutoPlan)

**注意:** RW排料逻辑在 `rwAutoPlan()` 方法中实现，与CP/WLT不同，它：
- 支持优先级分组处理
- 支持共享配置 (shareRrn)
- 支持直排和仓库排两种模式

**发现的问题:**
- 优先级处理逻辑较为复杂，需要充分测试
- 共享配置的并发控制需要验证

## 5. 边界条件验证

### 5.1 已验证的边界条件

| 边界条件 | 处理情况 | 状态 |
|----------|----------|------|
| 空配置列表 | 记录日志并返回 | 已处理 |
| 配置无效 | 关闭配置并记录 | 已处理 |
| 无待排批次 | 记录日志 | 已处理 |
| 批次已绑定 | 跳过并记录 | 已处理 |
| 数量超限 | 停止添加 | 已处理 |
| 异常中断 | 抛出异常 | 已处理 |

### 5.2 需要补充的边界条件

| 边界条件 | 风险 | 建议 |
|----------|------|------|
| 配置数量为0或负数 | 可能导致无限循环 | 添加前置校验 |
| 并发修改配置 | 数据不一致 | 添加乐观锁 |
| 数据库连接超时 | 任务挂起 | 添加超时处理 |
| 内存溢出 (大量批次) | 系统崩溃 | 分批处理 |

## 6. 性能分析

### 6.1 潜在性能瓶颈

| 位置 | 问题 | 影响 | 建议 |
|------|------|------|------|
| 批次查询 | 可能返回大量数据 | 内存溢出 | 分页查询 |
| 循环内数据库操作 | 每条批次都查WorkOrderRelation | N+1问题 | 批量查询 |
| 事务范围 | 整个排料过程在一个事务 | 锁持有时间长 | 缩小事务范围 |
| 日志记录 | 同步写入数据库 | 影响性能 | 考虑异步化 |

### 6.2 优化建议

1. **批量查询优化:**
```java
// 当前: 循环内单条查询
for (WmsMmsMaterialLot mLot : materialLots) {
    List<WorkOrderRelation> relations = prpSetupService.getWorkOrderRelationByMLoRrn(mLot.getObjectRrn());
}

// 优化: 批量查询
List<Long> lotRrns = materialLots.stream().map(WmsMmsMaterialLot::getObjectRrn).collect(Collectors.toList());
Map<Long, List<WorkOrderRelation>> relationMap = prpSetupService.getWorkOrderRelationByMLoRrns(lotRrns);
```

2. **分页处理:**
```java
// 对于大量批次，分批处理
int batchSize = 100;
for (int i = 0; i < materialLots.size(); i += batchSize) {
    List<WmsMmsMaterialLot> batch = materialLots.subList(i, Math.min(i + batchSize, materialLots.size()));
    processBatch(batch);
}
```

## 8. 改进建议汇总

### 8.1 高优先级 (必须修复)

1. **修复并发控制缺陷** - 使用ReentrantLock或分布式锁

3. **统一日志记录** - WltAutoPlanJob添加结束日志

### 8.3 低优先级 (可选优化)

8. **日志异步化** - 提升性能
